# Wazuh SIEM Deployment

## Overview

The home lab uses **Wazuh** as the primary Security Information and Event Management (SIEM) and endpoint-monitoring platform.

The Wazuh server is hosted as an Ubuntu virtual machine on Proxmox and provides centralized collection, indexing, analysis, and visualization of security telemetry generated by systems throughout the lab.

The server is:

```text
Hostname: wazuh01
IP Address: 10.0.0.7
Platform: Ubuntu Linux
Wazuh Version: 4.14.6
```

The Wazuh environment is used to monitor systems such as:

- Windows Server 2025 Domain Controller
- Domain-joined Windows workstations
- Windows Security Event Logs
- Sysmon telemetry
- Process execution
- User and group management activity
- Custom security detections

The long-term objective is to use the SIEM as the centralized visibility and detection layer for the entire home lab.

# Why Service Validation Matters

The Wazuh dashboard being reachable does not automatically prove that every SIEM component is healthy.

For example:

```text

       │
       X

```

The correct validation process is:

```text
Service Running
      │
      ▼
Agent Connected
      │
      ▼
Events Received
      │
      ▼
Events Searchable
      │
      ▼
Detection Rules Working
```

---

# Rule Troubleshooting

The custom rules did not work perfectly on the first attempt.

One configuration change caused the Wazuh Manager restart to fail.

This required troubleshooting the rule file before the manager could successfully restart.

The process reinforced an important principle:

> A syntax or logic problem in a custom SIEM rule can affect the monitoring platform itself.

Changes to detection logic therefore need to be tested carefully.

# Why Rule Order and Relationships Matter

Detection rules do not exist independently.

A broader rule can sometimes influence how a more specific rule behaves.

Conceptually:

```text
General Rule
     │
     ▼
Event Matches
     │
     ▼
Specific Rule
```

The rule hierarchy and matching conditions must therefore be understood when building custom detections.

# Detection Validation

A rule is not considered successful merely because the configuration file loads.

The actual goal is:

```text
Expected Activity
      │
      ▼
Expected Alert
```

The complete validation requires:

1. Generating known activity
2. Confirming the endpoint event
3. Confirming ingestion
4. Confirming correct rule match
5. Confirming the alert appears as expected

---

# False Positives

A useful detection should not alert on every normal administrative action.

Rules should be specific enough to identify interesting behavior without generating excessive noise.

Conceptually:

```text
Too Broad
   │
   ▼
Many Alerts
   │
   ▼
Alert Fatigue
```

The long-term goal is:

```text
Relevant Activity
      │
      ▼
Useful Alert
```

This requires testing and tuning.

---

# Detection vs Logging

A major lesson from building the SIEM was the difference between:

```text
Logging
```

and:

```text
Detection
```

Logging answers:

> What happened?

Detection answers:

> Which activity is security-relevant?

For example:

```text
Event ID 4688
```

only indicates that a process was created.

A detection rule provides the security context required to decide whether that process deserves attention.

# Example Missing Alert Investigation

Suppose a command is executed but no Wazuh alert appears.

The troubleshooting process is:

```text
Was the command executed?
        │
        ▼
Did Windows generate 4688 or Sysmon Event 1?
        │
        ▼
Did the Wazuh agent collect it?
        │
        ▼
Did Wazuh receive the event?
        │
        ▼
Was the expected field parsed?
        │
        ▼
Did the custom rule match?
        │
        ▼
Was the event indexed?
        │
        ▼
Does it appear in the dashboard?
```

This avoids immediately editing the rule when the problem may exist earlier in the pipeline.

---

# Wazuh Manager Restart Safety

After changing custom rules, the Wazuh Manager may need to reload or restart.

Because a malformed rule can cause service problems, configuration changes should be made carefully.

A safe workflow is:

```text
Backup Rule File
      │
      ▼
Make Small Change
      │
      ▼
Validate
      │
      ▼
Restart / Reload
      │
      ▼
Check Service
      │
      ▼
Generate Test Activity
```

---

# Service Health After Changes

After modifying Wazuh configuration, service status should be checked.

For example:

```bash
systemctl status wazuh-manager
```

If the service does not start normally, logs and the recently modified configuration should be reviewed before making additional changes.

# What I Learned

Deploying Wazuh demonstrated that building a SIEM requires much more than installing a dashboard.

A complete monitoring pipeline requires:

```text
Endpoint Logging
       │
       ▼
Agent Collection
       │
       ▼
Network Transport
       │
       ▼
SIEM Processing
       │
       ▼
Event Parsing
       │
       ▼
Detection Logic
       │
       ▼
Indexing
       │
       ▼
Investigation
```

The most important lesson was:

> **A detection can only be as good as the telemetry feeding it.**

Another major lesson was:

> **When an alert does not work, troubleshoot the entire event pipeline rather than assuming the rule itself is the problem.**

The Wazuh project transformed the home lab from a collection of infrastructure systems into an environment capable of centralized security monitoring and custom threat detection.
