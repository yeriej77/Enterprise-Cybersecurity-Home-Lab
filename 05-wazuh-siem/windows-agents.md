# Wazuh Windows Agents

## Overview

The home lab uses **Wazuh agents** on Windows systems to collect endpoint telemetry and forward it to the centralized Wazuh SIEM.

The Wazuh server is:

```text
Hostname: wazuh01
IP Address: 10.0.0.7
Wazuh Version: 4.14.6
```

Windows agents were deployed to:

```text
DC1
Client01
```

Both agents are currently online and sending security telemetry to the Wazuh server.

---

# Current Windows Agents

| Endpoint | Role | IP Address | Agent Version | Status |
|---|---|---:|---|---|
| DC1 | Windows Server 2025 Domain Controller | `10.0.0.6` | Wazuh `4.14.6` | Online |
| Client01 | Domain-Joined Windows Workstation | DHCP | Wazuh `4.14.6` | Online |

These systems provide two different types of security visibility.

```text
DC1
 │
 ├── Active Directory
 ├── DNS
 ├── DHCP
 ├── Group Management
 └── Administrative Activity


Client01
 │
 ├── User Activity
 ├── Process Execution
 ├── Command Execution
 └── Endpoint Security Events
```

# Agent Architecture

The communication model is:

```text
Windows Endpoint
       │
       ▼
   Wazuh Agent
       │
       ▼
Network Connection
       │
       ▼
   Wazuh Manager
     10.0.0.7
       │
       ▼
Event Processing
       │
       ▼
Wazuh Dashboard
```

The endpoint generates the telemetry.

The Wazuh agent collects and forwards it.

The Wazuh server analyzes and stores the information.

---

# Why Use Endpoint Agents?

Network monitoring alone cannot provide complete visibility into what happens inside a Windows system.

For example, a network sensor may see:

```text
Client01 → DC1
```

but it may not know that the user executed:

```text
powershell.exe
```

or:

```text
net.exe
```

The Wazuh agent provides endpoint-level visibility.

```text
User Activity
      │
      ▼
Windows
      │
      ▼
Event Log
      │
      ▼
Wazuh Agent
      │
      ▼
Central SIEM
```

# Why Monitor the Domain Controller?

A suspicious event on a workstation may affect one endpoint.

A suspicious action on a domain controller can potentially affect the entire domain.

Examples of important DC activity include:

```text
Account Creation
Group Membership Changes
Administrative Commands
Process Execution
Authentication Activity
```

For that reason, the DC1 Wazuh agent is a critical part of the monitoring architecture.

# Agent Registration

A Windows endpoint must become known to the Wazuh server before it can participate in centralized monitoring.

Conceptually:

```text
Install Agent
     │
     ▼
Configure Wazuh Server
     │
     ▼
Register / Enroll Agent
     │
     ▼
Start Agent
     │
     ▼
Agent Connects to Manager
```

Successful enrollment establishes the relationship between the endpoint and the SIEM.

---

# Agent Service

The Wazuh agent runs as a Windows service.

The service is responsible for maintaining communication with the Wazuh server and collecting configured telemetry.

A useful Windows service check is:

```powershell
Get-Service | Where-Object {$_.Name -like "*Wazuh*"}
```

The Wazuh service should be running when the endpoint is expected to send events.

---

```text
      │
      ▼

      │
      ▼
```


---

# Connected Does Not Mean Fully Monitored

One of the most important lessons from the agent deployment was:

> **An agent showing as online does not automatically prove that the specific logs required for a detection are arriving.**

For example:

```text
Agent Online
```

does not necessarily prove:

```text
Event ID 4688 Available
```

or:

```text
Sysmon Events Available
```

The required event source must also be enabled and collected.

---

# Monitoring Pipeline

A complete Windows monitoring pipeline is:

```text

      │
      ▼

      │
      ▼
```

# Searching by Agent

One of the simplest ways to investigate endpoint telemetry is by filtering events based on:

```text
agent.name
```

For DC1:

```text
agent.name: DC1
```

For Client01:

```text
agent.name: Client01
```

This separates events from one endpoint from the rest of the environment.

---

# Why Agent Filtering Matters

Without endpoint filtering:

```text
All Events
   │
   ▼
Large Event Set
```

With agent filtering:

```text
agent.name: DC1
       │
       ▼
Only DC1 Events
```

This makes troubleshooting and investigation significantly easier.

---

# Combining Filters

Agent filtering can be combined with event characteristics.

Conceptually:

```text
Agent = DC1
AND
Event ID = 4688
```

or:

```text
Agent = Client01
AND
Process = powershell.exe
```

This helps isolate specific activity from specific endpoints.

# Event Validation Workflow

When testing new telemetry, the workflow is:

```text
Choose Endpoint
      │
      ▼
Generate Known Activity
      │
      ▼
Verify Local Windows Event
      │
      ▼
Search Wazuh by agent.name
      │
      ▼
Locate Event
      │
      ▼
Inspect Fields
```

This confirms that the agent is collecting the expected data.

---

# Local Validation First

Before troubleshooting Wazuh, the event should be verified on Windows.

For example, recent Security Event ID 4688 events can be viewed with:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName='Security'
    Id=4688
} -MaxEvents 10
```

If Windows never generated the event, there is nothing for the Wazuh agent to collect.

---

# Sysmon Local Validation

Sysmon events can be checked using:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName='Microsoft-Windows-Sysmon/Operational'
    Id=1
} -MaxEvents 10
```

This confirms the Sysmon layer is functioning before investigating the agent.

---

# Troubleshooting Missing Events

If the Wazuh agent is online but an expected event does not appear, the troubleshooting path is:

```text
Expected Event Missing
       │
       ▼
Did Windows Generate It?
       │
   ┌───┴───┐
   │       │
  No      Yes
   │       │
   ▼       ▼
Audit    Check Agent
Policy   Collection
           │
           ▼
     Check Wazuh Search
           │
           ▼
       Check Fields
```

This prevents the agent from being blamed for an endpoint audit-policy problem.

---

# Troubleshooting Agent Connectivity

If an endpoint appears offline, troubleshooting should begin with the service and network path.

```text
Wazuh Service Running?
        │
        ▼
Correct Manager Address?
        │
        ▼
Can Endpoint Reach 10.0.0.7?
        │
        ▼
Agent Registered?
        │
        ▼
Manager Receiving Connection?
```

The issue may exist on either the endpoint or the network.

---

# Network Dependency

The agent depends on network connectivity between the Windows endpoint and:

```text
10.0.0.7
```

Conceptually:

```text
Windows Endpoint
      │
      ▼
VLAN 10
      │
      ▼
Network
      │
      ▼
Wazuh
10.0.0.7
```

If the network path fails, the agent cannot send telemetry even if its Windows service is running normally.

---

# DNS vs IP Troubleshooting

Because the Wazuh server has a known static address:

```text
10.0.0.7
```

IP-based testing can help separate DNS problems from connectivity problems.

For example:

```powershell
ping 10.0.0.7
```

If IP connectivity works but a hostname-based connection does not, DNS should be investigated separately.

# Agent vs Detection Rule

An important distinction is:

```text
Agent
```

collects and forwards the telemetry.

A:

```text
Detection Rule
```

decides whether the activity should create a security alert.

Therefore:

```text
Event Present
+
No Alert
```

usually means the detection logic should be investigated rather than immediately changing the agent.

---

# Troubleshooting Example

Suppose:

```text
net.exe
```

is executed on Client01 but the expected custom alert does not appear.

The correct workflow is:

```text
Did net.exe run?
      │
      ▼
Was 4688 / Sysmon Event generated?
      │
      ▼
Can the event be found under:
agent.name: Client01?
      │
      ▼
Does the event contain the expected process field?
      │
      ▼
Does the custom rule reference that field correctly?
```

This isolates the problem logically.

# Security Considerations

Endpoint agents themselves should be treated as part of the security infrastructure.

If an attacker can disable or modify monitoring:


# What I Learned

Deploying Wazuh agents reinforced that:

> **An agent being online and an agent collecting the telemetry you need are two different things.**

A complete validation requires:

```text
Agent Installed
      │
      ▼
Agent Online
      │
      ▼
Windows Generates Event
      │
      ▼
Agent Collects Event
      │
      ▼
Wazuh Receives Event
      │
      ▼
Event Can Be Searched
      │
      ▼
Detection Can Use It
```

Another important lesson was:

> **Always verify telemetry at the source before troubleshooting the SIEM.**

This significantly reduced guesswork when building and troubleshooting custom detections.
